# goPine 0.3.26 candidate

After the 0.3.25 transfer, the user reported working phone notifications but
InfiniLink remaining **Connecting** with an empty device list. Pairing was
initiated inside InfiniLink. Notification delivery is physically confirmed;
InfiniLink's completed connection state is not.

This candidate restores the pinned InfiniTime Battery service behavior:
`0x2A19` immediately returns the current one-byte percentage, without waiting
for encryption. The existing READ/NOTIFY properties and notification behavior
are preserved. Time, weather, music and alert writes retain their separate
authentication checks.

The audited InfiniLink `rebuild` development source reads Battery once during characteristic
discovery, subscribes, and sets `hasLoadedBatteryLevel` only when a value arrives.
A failed initial read is logged without an app retry. Its connection label can
therefore remain **Connecting** while iOS ANCS delivery works. goPine's additional
Battery encryption gate diverged from the reference and could withhold that
first response until the battery percentage later changed. The new code removes
that gate rather than depending on an extra read that the app does not make.

Follow-up on 2026-10-11: the user's three-tab interface matches classic 1.0.2,
which instead requires a nonempty firmware revision. This audit did not cover
that release's readiness condition; see [0.3.27](0.3.27.md).

Reference sources:

- InfiniTime commit `6c119eb52206b580b556b41633dddc1e1b66a8da`,
  `src/components/ble/BatteryInformationService.cpp`.
- InfiniLink commit `60abe2d2c67aff67726855374385a499d9353a94`,
  `InfiniLink/BLE/BLEManager.swift` and `BLECharacteristicHandler.swift`.

Validation:

- The real pinned-host regression performs the app's single Battery read and
  subscription before Secure Connections pairing. It receives the current 80%
  value immediately, without changing the percentage or retrying after pairing.
  Eight bonded reconnects also read Battery before encryption restoration.
- Restoring the old gate fails that exact initial-read test: the host returns an
  ATT error instead of a Battery Read Response.
- Unauthenticated time, weather, music and alert writes still return the ATT
  authentication error and queue no data.
- Full host ASan/UBSan integration and all 11 port sanitizer suites pass.
- The physical harness now checks ten source-derived UUID/property expectations,
  performs the one-time Battery read/subscription, and independently requires
  fresh authenticated, bonded encryption metadata. Public Battery data never
  counts as security proof. All 42 Python harness/decoder tests pass, including
  negative controls for missing GATT and security validation.
- TinyGo build/resource gates pass: image 289,604 bytes; reserved RAM 23,412;
  heap region 42,124; task stack 8,192. Package SHA-256:
  `cf247c129eaaf40f2c7f709449405cdd2b5fde9c325894ce1e3977c08c36b438`.

Physical InfiniLink completion on 0.3.26 still needs verification. The initial
upload and one retry could not detect the watch through the configured `hci1`
adapter; both stopped before any firmware was sent. Logs:
`build/ota/upload-0.3.26.log` and `build/ota/upload-0.3.26-retry.log`.
After the user reopened **Ready to connect**, the watch received and verified
all 289,604 bytes through the in-app updater on 2026-10-10. The transfer resumed
after an initial interruption and exited successfully; evidence is
`build/ota/upload-0.3.26-retry2.log`. The PC was disconnected, unpaired, unbonded
and untrusted afterward. The saved phone pairing was retained. INSTALL, boot
and KEEP have not been reported, and InfiniLink completion remains unconfirmed.

The subsequent PC-tool correction handles an already-connected watch before
scanning. The previous uploader required a fresh advertisement even though a
connected watch stops advertising; it could therefore overlook a usable BlueZ
connection. The sender now checks only the configured adapter/address and
reuses that connection without pairing. A shared target lock covers the Linux
sender and both pairing diagnostics through disconnect cleanup. These are PC
tool changes and do not alter the verified firmware package. They reproduce a
case raised by the user, but do not establish the cause of earlier timeouts;
the watch's BlueZ Device1 was absent in the earlier status snapshot.

All 79 sender, updater, pairing and target-lock tests pass. The new regression
completes a simulated transfer over an existing PC connection without any
advertisement; restoring the old scan-only selection makes it time out.
Process-level tests verify exclusion through cleanup and release after process
exit, while other adapters/devices remain available. The test run used no
Bluetooth hardware; log: `build/ota/pc-bluetooth-regression-0.3.26.log`.
