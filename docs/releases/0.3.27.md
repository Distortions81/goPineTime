# goPine 0.3.27 candidate

The user reports that Bluetooth works but InfiniLink never finishes displaying
the watch. Their **Home, Charts, Settings** tabs match the classic 1.0.2 source.
The previous audit used the newer `rebuild` branch (`60abe2d2`), whose readiness
condition is different. The installed app version was not separately reported.

Classic InfiniLink 1.0.2 requires a connected peripheral **and a nonempty firmware
revision** before replacing its Connecting screen with Home. It reads this
revision from the standard Device Information characteristic `0x2A26`. goPine
provided Battery and phone features but omitted Device Information entirely, so
Battery reads and iOS notifications could work while this condition never passed.

The source used for this regression is official InfiniLink commit
`d9f13a5d785b25b30870eb6ea99d4716b554a9b0`, dated 2022-11-03. Its Xcode project
declares version 1.0.2 and its ContentView has the user's three tabs:

- [WelcomeView](https://github.com/InfiniTimeOrg/InfiniLink/blob/d9f13a5d785b25b30870eb6ea99d4716b554a9b0/InfiniLink/View%20Components/Home%20View/WelcomeView.swift)
  gates Home on connection and a nonempty firmware string.
- [DeviceInfo](https://github.com/InfiniTimeOrg/InfiniLink/blob/d9f13a5d785b25b30870eb6ea99d4716b554a9b0/InfiniLink/BLE/DeviceInfo.swift)
  reads the public Device Information characteristics and decodes firmware as UTF-8.

The candidate adds public, read-only Device Information (`0x180A`): model
`PineTime`, manufacturer `PINE64`, and firmware `goPine ` followed by the actual
build version. It appends the service to preserve all existing attribute handles.
It does not claim to run InfiniTime or add InfiniTime's firmware-update protocol.
The existing goPine in-app updater remains the update path.

To refresh a saved phone's service cache, initial host registration marks the
standard Service Changed range pending. It is delivered after the bonded phone
restores encryption and acknowledges the indication. An unrelated PC update
connection cannot consume it, and ordinary mode changes do not repeat it.
The migration requires a previously saved Service Changed subscription; it
cannot reconstruct one already lost by older firmware.

The cold-boot regression exposed a pinned NimBLE RAM-store defect: deleting a
middle subscription shifted a record count as bytes, corrupting the following
subscription. The local store wrapper now shifts complete CCCD records. A test
deletes Music before Service Changed, reloads the flash journal, and verifies
the complete surviving subscription and both phone keys. The two-device extension below migrates the old journal while preserving
existing security keys.

The classic app also stores firmware in a field that does not publish a UI
change. Because the new service follows Battery, the firmware callback could
arrive after the initial Battery update and leave Home stale. After a successful
normal Firmware Revision read, Phone mode sends one current Battery sample to
an already subscribed connection. It queues this after the read response, does
not sample the ADC, and does not repeat until a new connection. Unsubscribed
reads and invalid Read Blob requests do not trigger it. The real-host test
asserts the two ATT packets' order and the one-notification limit.

Classic 1.0.2 has no weather sender or Force ANCS setting. Its supported time,
alert, and music encodings match goPine; steps and heart-rate characteristics
remain unavailable. Those feature limits are separate from the missing
firmware-revision condition that blocked Home.

## Multiple devices and OTA coexistence

The user requested this extension before flashing: support multiple saved paired
devices and keep OTA reachable when phones reconnect automatically. Phone mode
has two independent feature contexts and two durable bond slots. Update mode
has three live connection slots, allowing both saved devices and the explicit
updater to connect concurrently. An OTA status subscription, including one
restored from a saved CCCD, never owns a transfer. Only an accepted BEGIN or a
matching DATA/VERIFY resume claims ownership; other connections cannot write,
clear the owner's queued data, or change its MTU/status delivery. Non-owner
candidates have a bounded 15-second grace; a subscribed verification waiter
gets one 60-second grace because the maintained uploader waits up to 45 seconds.

Time, weather, Music and ANS mailboxes are per device. Music commands retain the
source connection's generation. Each Apple ANCS client has its own discovery,
request, response and queue state; the Go inbox scopes remote notification IDs
by source, so equal IDs or a disconnect cannot alter another device's messages.
Cancelling a pairing disconnects only that device. INFO displays a saved-device
count, and the destructive control explicitly says FORGET ALL.

Two security-procedure slots permit overlapping saved-key restoration. Fresh
pairing is still serialized to one PIN prompt. The real-host test reproduced a
missing LTK reply when the second device restored first with only one security
slot; that ordering is retained as a regression.

The bond journal moves from a 240-byte schema-1 payload to a 464-byte schema-2
payload inside the existing 512-byte records and single reserved flash page.
Loading old keys does not erase or rewrite them. The next committed append
migrates them; interrupted migration and later two-device appends preserve the
prior committed record. The pre-existing power-loss risk during whole-page
reclamation remains. Two keys per device and eight subscription records are
retained, without silently replacing a saved device when capacity is full.

The first three-connection build failed the existing 40 KiB heap floor. The
host allocator measured a 3,056-byte peak with 64-bit pointers; reducing its
reservation from 8 to 5 KiB retains over 2 KiB of tested allocator headroom and
recovers the original heap budget. The shared eight mbufs and four controller
credits remain unchanged. Repeated subscription writes cannot indefinitely
postpone saving newly paired keys: the commit deadline is bounded from the
first dirty store write.

## Validation

Validation on 2026-10-11:

- Full pinned-host ASan/UBSan suite: actual two-device SC pairing and durable
  restoration in reverse order, concurrent ANCS requests and fragmented
  replies, source isolation, pairing cancellation, and three-link OTA with
  shared-buffer pressure. Existing classic DIS/Battery ordering, cache
  migration, 100 OTA cycles and eight private-address reconnects remain covered.
- Twelve port ASan/UBSan suites, including 128 interrupted migration boundaries
  and 128 later interrupted two-device append boundaries.
- Negative controls detect missing second-slot advertising, missing OTA owner
  authorization, global ANCS reset, missing old-key migration, broken security
  record compaction, and repeated false wakes from alternating SMP progress.
- 74 Python uploader, pairing harness, decoder and session-lock tests;
  `go test -race ./...`, `go vet ./...`, and rendered pairing/count/reset screens.
- ARM build and package hash/MCUboot validation. Image: 295,892 bytes.
  Reserved RAM: 23,924 bytes; heap region: 41,612 bytes; task stack: 8,192 bytes.
  Selected pairing/controller path: 4,872 bytes plus a 2,048-byte reserve.
  The resource limits were not lowered. These are static regression budgets,
  not measured physical free memory.

## Physical transfer status

Two upload attempts on 2026-10-11 timed out before reaching the watch; neither
sent firmware (`build/ota/upload-0.3.27.log` and `upload-0.3.27-retry.log`). A
subsequent hci1 diagnostic detected nine advertisers but no watch; BlueZ had no
connection to the watch on any adapter. This does not by itself identify the
phone as the cause.

The user agreed to temporarily turn phone Bluetooth off, then requested fixing
OTA coexistence before flashing. The third uploader was interrupted immediately.
It had accepted BEGIN and reported zero acknowledged image bytes, followed by
ATT error `0x0e`; no image was verified or installed
(`build/ota/upload-0.3.27-retry2.log`). Unacknowledged attempted bytes are not
established by that log. That attempted package preceded the multiple-device extension and has been
replaced by the rebuilt package recorded above.

Physical InfiniLink completion, installation, boot and KEEP remain unverified.
Automated Linux and simulated-host checks do not execute the installed app's
CoreBluetooth or SwiftUI behavior.

The rebuilt multi-device package was attempted through the normal in-app updater
(`build/ota/upload-0.3.27-multiple.log`). The installed firmware repeatedly
disconnected during GATT service discovery, before BEGIN or any image bytes.
The attempt was stopped pending reopening the watch update session. No transfer
validation, installation, boot or KEEP is established for this package.

After the user reopened Ready to connect, the rebuilt package transferred fully
and the watch verified all 295,892 bytes on 2026-10-11. The successful retry had
no reconnects and took about 3 minutes 3 seconds from upload-log creation through
the final success message, including connection setup and receiver verification.
That is about 1.58 KiB/s end to end on the installed pre-0.3.27 receiver, not an
isolated radio throughput measurement or a before/after speed comparison.
Evidence: `build/ota/upload-0.3.27-multiple-retry.log` and
`build/ota/validation-0.3.27/transfer.json`. INSTALL and KEEP were instructed;
physical boot/KEEP and InfiniLink Home completion remain unconfirmed.
