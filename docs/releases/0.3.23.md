# goPine 0.3.23 candidate

The user reports that pairing still fails on 0.3.21 and the PIN usually never
appears. INFO shows No saved phone. Earlier host-test passes are not physical
InfiniLink validation.

This candidate fixes a reproduced retry defect: the first disconnect immediately
abandoned fast advertising, and CONNECT PHONE did not restore it while the radio
was already running. Opening/waking Phone or tapping CONNECT renews a bounded
30-second fast window in place; active connections and SMP are preserved. Phone
fast advertising matches InfiniTime's 20–30 ms range. Failed retries remain fast
until the existing window expires, then return to slow advertising.

First pairing uses the reference central-triggered flow (ANCS security or an ATT
authentication error from protected Battery/phone features). goPine no longer
immediately sends a Security Request to an unbonded peer on CONNECT. Saved peers
still support requested key restoration. The effect of the previous proactive
request on iOS remains unverified; cryptography and trust requirements are intact.

A bounded non-secret GATT trace retains the actual pairing events across retries
and an OTA handoff. Failed CONNECT, security initiation and PIN injection errors
now also remain visible through INFO. The physical BlueZ pairing harness records
whether the watch reaches the central's RequestPasskey, rejects before PIN entry,
and never saves a PC bond. See [pairing diagnosis](../pairing.md).

The candidate includes the prepared 0.3.22 native OTA protocol-2 improvements and
legacy uploader removal. Emergency bootloader recovery and rollback are preserved.
The first upgrade from the watch's protocol-1 receiver uses the locally prepared
one-time in-app sender, with INSTALL then KEEP.

Validation:

- Restoring the original unconditional slow-advertising policy reproduces the
  fast-retry test failure; the corrected policy passes. Connected setup refresh,
  bounded expiry, retained failed-CONNECT diagnostics and trace reads through
  an OTA-mode handoff pass in the real pinned host.
- Delayed controller completion retains all four TX slots while GATT discovery
  and fragmented SMP public-key reception overlap; the PIN stage succeeds with
  existing buffers. No buffer-size change is made.
- Go race tests and vet, eleven C sanitizer suites, complete simulated SC bonding,
  private-address reconnects and ANCS integration pass. Trace decoder tests pass.
- TinyGo build and resource gates pass: image 288,636 bytes, reserved RAM 23,412
  bytes, heap region 42,124 bytes, task stack 8,192 bytes. Selected pairing path
  4,856 bytes plus 2,048-byte reserve. These are regression budgets, not measured
  physical stack/heap peaks.
- Package SHA-256: `905e8e4c9f7280653b127f06506306e96cacf88dd99e89cf418f0caf2be98366`.

The in-app transition uploader sent all 288,636 bytes on 2026-10-10 and the watch
verified the image. Log: `build/ota/upload-0.3.23-transition-20261010-204440.log`.
Boot and KEEP have not been explicitly confirmed by the user.

Three physical probe runs on hci1 each failed to discover the configured watch
address in all three attempts, before any connection or SMP exchange. A separate
scan saw nearby BLE devices but no watch advertisement. Logs:
`build/ota/pairing-physical-0.3.jsonl` and
`build/ota/pairing-20261010-205327-998636.jsonl` and
`build/ota/pairing-20261010-205633-512642.jsonl`.
The attempted btmon capture could not bind its monitor socket due to permissions;
it contains no usable packets. A bounded discovery wait for a read-only OTA trace
also saw no watch; no trace was read. Mode clarification is pending. These results
do not establish successful physical pairing or the reason advertising was absent.
