# goPine 0.3.25 candidate

The user can reach the PIN after forgetting both saved pairings, but the watch
briefly shows **Connected**, then **Retrying**, and does not finish connecting in
InfiniLink. This candidate fixes a reproduced failure when Bluetooth restarts
after a successful bond. Physical InfiniLink success is still unverified.

## Bonded restart fix

The pinned NimBLE host restores saved peer identity keys before calling the
application's sync callback. goPine then inserted the same identity again. The
real controller rejects duplicate entries with HCI status `0x12`, surfaced as
NimBLE `0x0212` (530), leaving advertising disabled. The previous host harness
incorrectly replaced duplicate entries, hiding this failure.

The checked restore now removes the existing controller entry before adding it
again, tolerating only the controller's explicit absent-entry response. Stored
phone keys remain unchanged; other HCI errors remain visible. Tests now match
the controller's duplicate rejection, capacity and removal behavior, and require
successful advertising before each of eight bonded private-address reconnects.

A normal coalesced settings save stops and restarts Bluetooth once pairing has
completed, so this bug can turn the first **Connected** state into **Retrying**.
The same startup path also affects OTA availability while a phone bond exists.
This is a reproduced mechanism matching the report, not physical confirmation
that it is the only remaining fault.

## Other changes

- A due bond-journal save wakes the application loop from its controller-only
  input wait. Previously the zero sleep deadline could spin without saving
  until unrelated application work arrived.
- Non-secret trace events record missing saved-key lookups, early Pair Request
  rejections and failures before advertising. No keys, PINs or peer addresses
  are exposed. The bounded ring remains 24 records.
- The PC harness classifies known connection and timeout failures without
  logging arbitrary exception text. The firmware harness now tests a negative
  LTK reply followed by successful fresh PIN negotiation on the same link.

## Validation and physical evidence

- A negative control with the real controller's duplicate rejection reproduced
  `failure=530`, `synced=0`, with a saved bond. The corrected implementation
  passes the pinned-host ASan/UBSan integration.
- The journal-deadline regression fails without the wakeup fix. Removing either
  early-security trace hook independently fails its regression.
- All 11 port sanitizer suites and 38 Python harness/decoder checks pass.
- TinyGo build/resource gates pass: image 289,692 bytes; reserved RAM 23,412;
  heap region 42,124; task stack 8,192; selected pairing path 4,856 plus a
  2,048-byte reserve. These are static budgets, not measured peak usage.
- Package SHA-256:
  `6814ebddcbd8a83eb2f31382b57e95dff2e3b6c6a2f40aa7f9457eac16105ea3`.
- A saturated 196-byte trace read at MTU 247 passes with controller-shaped RX
  buffers, four delayed ACL fragments and up to three buffers held by unrelated
  work. The 16-byte OTA status read also passes while every other msys buffer is
  occupied. These do not reproduce or resolve the physical ATT `0x0e` observation.
- After the user's permission to remove only the PC's saved bond, a complete
  188-byte OTA trace read succeeded. It showed old unauthenticated keys, a later
  empty watch key store and authentication-failure disconnects before PIN.
  Evidence: `build/ota/pairing-retained-0.3.24.json`.
- The user then confirmed that a PIN appeared and the watch briefly connected
  after clearing both sides, followed by **Retrying**. Later OTA trace reads
  failed with an ATT `0x0e` error or disconnected during service discovery.
  Evidence: `build/ota/pairing-0.3.24-post-pin-retries.log`.

The first authorized 0.3.25 upload failed before firmware DATA was sent. Its
initial connection reported ATT `0x0e`; retries disconnected during service
discovery until the 90-second deadline. No uploader remained running afterward.
Log: `build/ota/upload-0.3.25.log`. The user was asked to clear the on-watch bond
once and reopen OTA, because the installed firmware's shared startup path can
reject the duplicate identity before advertising. The prepared package is
unchanged.

After the user cleared the watch bond and reopened OTA, the retry on 2026-10-10
sent all 289,692 bytes and the watch verified the image. An initial ATT `0x0e`
was followed by a successful reconnect and complete transfer. Log:
`build/ota/upload-0.3.25-retry.log`. Transfer and receiver validation are
confirmed; installation, boot and KEEP have not been reported. The user was
instructed to tap **INSTALL**, then **KEEP** after reboot. Because the watch bond
was cleared for this upload, its old iPhone Bluetooth entry must also be
forgotten before a fresh pairing. Physical InfiniLink completion remains
unverified.

ATT `0x0e` alone does not prove a firmware TX failure: BlueZ can also synthesize
it locally, including on GATT cache errors. Simulated host tests do not establish
physical InfiniLink/iOS interoperability.
