# goPine 0.3.24 candidate

Pairing still fails physically: the user reports no PIN, or a PIN appearing only
after a long delay and never completing. The retained 0.3.23 trace was recovered
through OTA on 2026-10-10. It records repeated HCI authentication failures (0x205),
sometimes after encryption succeeds without reaching the required authenticated,
bonded link state. This is physical evidence of security failure, not proof of
which saved key or peer caused it.

This candidate fixes reproducible defects and provides an
[automated pairing harness](../pairing-harness.md):

- Reject unsupported PIN associations, keys below 16 bytes and nonbonding
  requests before Pair Response. The pinned stack otherwise permits Just Works
  without a PIN even with MITM requested. Invalid completion cannot save weak
  keys into the single phone slot as a second layer of protection.
- Preserve existing unusable saved records, show **Pairing needs reset** in
  Phone → INFO, and offer the confirmed **RESET PAIRING** action. Firmware does
  not silently erase or replace a previously saved bond.
- Service the Bluetooth controller during touch reset/wake, LCD settling and
  flash waits. Queued controller work no longer waits through a 55–125 ms hardware
  delay. Host callbacks remain deferred. The upstream LCD driver's internal
  5 ms sleep remains; the 1 ms cooperative sleep slices are not measured radio
  latency guarantees.
- Retry initial ANCS memory exhaustion at one-second intervals within a
  15-second budget. Keep pending notification IDs, and wake the main host pump
  when ANCS deadlines are due. Ambiguous sent operations still fail instead of
  being replayed.
- Retain actual security flags, key strength and saved/matching-peer metadata
  in the bounded non-secret trace. OTA encryption does not overwrite Phone's
  last failure. No PIN, key material or peer identifier is exposed.

The harness uses the configured hci1 adapter. Its unattended probe reaches the
central PIN request and deliberately rejects before saving a bond. Explicit
full mode asks for one hidden PIN, then checks encryption, authentication, bond
state, fresh reconnect evidence and optional feature writes. It initiates Pair
through its scoped agent before GATT discovery to avoid BlueZ's automatic
Battery pairing through the default agent. It never removes existing PC bonds.

Validation:

- 29 harness tests and four trace decoder tests pass, including false-success,
  stale reconnect evidence, partial trace, cancellation and cleanup failures.
- Eleven sanitizer suites pass. Original weak-bond persistence fails the new
  negative regression; fixed code passes. Invalid journal records survive
  reboot unchanged and remain available for explicit reset.
- Real pinned host/crypto integration passes 11 rejected Pair Request cases,
  valid PIN retry on the same connection, the complete 20-round passkey
  exchange, bond save/reload, eight private-address reconnects, ANCS and feature
  traffic, and 100 host restarts. Full 196-byte trace reads pass at MTU 23.
- Go tests/race checks and vet pass. Restoring raw hardware sleeps makes the
  controller-service regression fail in touch wake/sleep, LCD and flash cases.
- TinyGo build/resource checks pass: image 289,580 bytes; reserved RAM 23,412;
  heap region 42,124; task stack 8,192; selected pairing path 4,856 plus a
  2,048-byte reserve. These are budgets, not physical peak measurements.

No physical InfiniLink pairing success is claimed. Firmware transfer validation,
boot and KEEP are recorded separately below.

The authorized in-app upload was attempted on 2026-10-10. Connections repeatedly
dropped during service discovery; the uploader reached its deadline without
sending firmware or receiving an image-validation result. Log:
`build/ota/upload-0.3.24.log`. The user then reopened **Ready to connect** for a
retry with the same prepared package.

A subsequent read-only BlueZ check confirmed hci1 is powered, the configured
watch is not blocked, and no watch connection or resolved services remain. The
PC reports a saved/trusted bond; its cached name is InfiniTime, which does not
prove the current on-watch mode. The service journal reports only "No matching
connection for device". These checks do not justify toggling adapters or erasing
keys. The uploader already uses its discovered BLEDevice; its failure occurs
while waiting for BlueZ service resolution, before firmware DATA writes.

The installed BlueZ 5.72 also forces medium-security (encrypted) connection setup
when its local device record is paired, including for unprotected OTA services
([upstream device.c](https://github.com/bluez/bluez/blob/5.72/src/device.c)).
Consequently mismatched saved PC/watch keys remain a possible cause of the
pre-discovery disconnect. No keys have been removed; the log alone does not
prove that hypothesis.

The retry on 2026-10-10 succeeded without removing the existing PC bond. The
uploader sent all 289,580 bytes, reported **Watch verified the image**, and exited
successfully. Log: `build/ota/upload-0.3.24-retry.log`. This confirms the 0.3.24
transfer and receiver validation. The user was instructed to tap **INSTALL**,
then **KEEP** after reboot; installation, boot and KEEP have not been reported.
Physical InfiniLink pairing and feature delivery remain unverified.
